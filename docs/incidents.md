## 2026-10-29：常驻转发内存耗尽导致桌面严重卡顿

- 状态：已修复并部署已复现的队列增长机制；现场内存分配根因未最终确认，保留验证边界。
- 症状：使用 Brave 的 ChatGPT 网页应用浏览对话时，全机鼠标迟缓、Super 键无响应及机身发热，随后恢复。
- 影响版本：本机 tdssh 0.1.0，iroh 固定 1.3.0 / noq 1.3.0；运行二进制的精确构建提交尚未证实。
- 现场证据（Asia/Shanghai）：10:45:43 内核记录页面分配失败，8 GiB swap 的空闲量为 0；10:46:11 systemd-oomd 记录 tdssh 常驻转发服务占用 26.2G 并终止服务；10:46:23 服务自动重启后恢复到约 25 MiB。Brave 随后有被终止记录，但无法确定发出信号的一方。
- 历史检查：本仓库此前无 incidents 文件；已阅读 docs/validation.md 的传输、半关闭和断线退出调查。旧 stdin 阻塞退出故障与本次内存增长机制不同。
- 代码缺陷已复现：iroh 1.3.0 的路径重试队列未去重；同一远端存在多条连接、路径额度耗尽时，每轮重试可重复入队并几何增长。本机依赖源码存在同一逻辑；现场未采集到分配堆栈或对应错误，不能据此断言本次唯一根因。
- 上游参考：[问题 #4509](https://github.com/n0-computer/iroh/issues/4509)、[修复 #4551](https://github.com/n0-computer/iroh/pull/4551)。
- 本机恢复与防护：系统自行终止并重启服务；排查期间先设运行时 MemoryHigh=512M、MemoryMax=1G、MemorySwapMax=256M，已核对实际 cgroup 值。部署时将这些限制保存到本机私有 unit；触限可能中断转发连接。这是额外的影响范围限制，不等于证明所有增长来源已修复。私有服务配置、回退程序和完整现场记录仅留本机。

### Swap 的后续观察

压力解除后仍有约 4.1 GiB swap 占用，分散在 Java、IDE、PDF 阅读器和其他应用中。采样时可用内存约 23 GiB，后续每秒采样的 `vmstat so` 均为 0，内存 PSI 的 `avg10` 为 0；说明当时没有继续大量换出。未执行 swapoff，也未通过清空交换区来掩盖程序内存增长。

### 用户请求的按需生命周期

核对本机 SSH 有效配置及 systemd 引用：仅相关目标的 ProxyCommand 会触发 tdssh，普通 SSH 没有启动规则；当前 unit 为 static，旧常驻 unit 已禁用。用户选择“相关 SSH 全部断开后空闲 60 秒退出”。

增加可选 `forward --idle-timeout 60`，按活动转发会话计数，而非按无流量时长关闭连接。初次空闲和最后一条会话结束后启动倒计时；新会话取消倒计时。默认常驻转发 API、未使用此选项的 CLI 和服务端行为不变。本机 unit 设为 `Restart=no`，失败后也等待新的相关 SSH 请求，不自动拉起。

3 项真实本地 QUIC 生命周期回归验证首次空闲退出、安静的活动会话不被关闭、最后会话结束才计时、新会话取消计时，以及默认模式保留常驻行为。原程序中正在使用的相关连接经用户同意后切换；运行参数已确认包含 `--idle-timeout 60`。应用在后台保持或重新请求相关 SSH，同样算活动连接，不能承诺“未手动打开终端就绝不启动”。

安装后另用临时身份、独立端口及 `--no-relay` 执行真实 CLI 空闲验证：配置 60 秒后在 60.006 秒正常退出，退出码 0；没有占用用户连接。私有 unit 的 systemd 语法校验通过。安装包脚本验证新保留的 iroh MIT、Apache-2.0、BSD 许可及故障记录都包含在归档中；未发布该归档。
